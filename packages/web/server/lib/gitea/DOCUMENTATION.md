# Gitea integration

This module owns OpenChamber's first-party Gitea connection, issue/PR reads, comments, and PR creation. `feature-routes-runtime.js` registers `routes.js`; the web API wrapper reaches these routes through `runtimeFetch`. Web, desktop, hosted, and paired mobile therefore use the same server-side credentials. The VS Code runtime does not expose `RuntimeAPIs.gitea` yet.

`storage.js` keeps one token per normalized instance URL in `OPENCHAMBER_DATA_DIR/gitea-auth.json` (or `~/.config/openchamber/gitea-auth.json`). New tokens are verified against `/api/v1/user` before replacing an existing connection. Writes use an atomic rename and mode `0600`. Route responses contain only the instance URL and account login.

`repo.js` resolves the active directory from Git fetch remotes, trying `origin` first unless a route names a specific remote. It matches host, configured URL path, and HTTP(S) port before using a saved token. SSH remotes match host and path; if more than one saved instance could match, resolution fails. A missing match returns 404 instead of guessing from an `owner/repo` string. The picker uses the Git panel's nested-repository selection, then resolves every configured remote in that repository and lets the user choose among connected Gitea repositories.

`client.js` builds API paths from the saved instance URL, sends the token only to that origin, disables redirect following, limits a request to 10 seconds, and rejects responses above 4 MB. The routes normalize items and construct their browser links from the matched instance. The picker sends its selected remote and search text to `GET /api/gitea/items`; Gitea 1.24's repository issue endpoint searches issues with `type=issues` and pull requests with `type=pulls`. Unfiltered PR browsing still uses the PR list endpoint. Search remains inside the resolved repository, including private repositories. List failures remain errors, rather than appearing as an empty list. List and comment pagination use Gitea's `Link` header when available, even when a page is shorter than the requested limit; older servers without that header use the requested page size. Link URLs are never followed. Detail requests read up to 100 comments across at most 10 pages and mark partial comment content. PR diffs are fetched only when the picker asks for one; an expected instance/repository identity prevents a changed remote from attaching another repository's diff.

The composer stores Gitea issue and PR context with the instance URL, owner, repository, number, and canonical URL in `gitea-issue` / `gitea-pr` metadata. It uses the existing linked reference snapshot for the session row.

The pull request panel shares its creation form with GitHub. `POST /api/gitea/pr/create` resolves the target and source Git remotes on the server, requires both to match the same saved Gitea instance and repository name, and posts to the resolved target. `GET /api/gitea/pr/status` checks open PRs for the source branch. Creation needs a token with `write:repository`; `read:issue` and `read:user` remain needed for issue context and connection verification. Gitea 1.24 has no draft field in its create API, so Draft prefixes the title with `WIP:`.

Status checks open PRs first, then the two most recent pages of closed PRs sorted by close time. They match the head branch and source repository, and return confirmed draft/merge fields with the result. If older closed pages remain, `historyIncomplete` is true rather than claiming the branch has no PR history. The UI status store keys results by runtime, directory, branch, instance, repository, target remote, and source remote. A failed refresh preserves the last confirmed result; a successful empty result replaces it.

`GET /api/gitea/item` includes confirmed PR draft/merge, branch and head-commit fields, plus issue-style comments. Review comments and commit statuses load separately, on demand, from the Gitea review and combined-status APIs. Each section can fail or be refreshed without hiding the PR overview. Gitea returns `statuses: null` with `total_count: 0` for a confirmed empty check list. The UI polls while a loaded check list is running and lets individual comments or failed checks be pinned to chat with an instance-qualified label.

`POST /api/gitea/comment` accepts an expected instance and repository identity and re-resolves the selected Git remote before posting. A changed repository returns 409 instead of posting to the new target. Commenting requires `write:issue`; failed posts leave the UI draft intact.

PR capabilities come from a fresh PR and repository read, including the account's repository permissions and allowed merge methods. Before edit, ready, or merge, the server re-resolves target and source remotes and verifies the expected instance, repository, source branch, and head SHA. Draft-to-ready removes a leading `WIP:` or `[WIP]` through Gitea's PR edit API and requires Gitea to confirm `draft: false`. Merge requires repository write permission, an enabled method, and a mergeable, non-draft PR; it fetches the PR again to confirm the merged result. UI edits stay typed on failure. This behavior was validated against Gitea 1.27.3; older server versions have not been acceptance tested.
